# P252–P256 and P257–P258 qualification (2026-09-28)

There are two candidates, each exported with `git archive` into
`scratch/p256_qual_20260928/{cand,p258}`. The working tree was never used.
The baseline is `0b2d265` in every comparison. The `3c3ade8` column holds
the P250+P251 numbers from `docs/perf/p250_p251_fpu_issue/`, which were
made with the same recipe.

- **A. `b2ed1b08f615c51c87389630e2183055f2a8d877`** (`b2ed1b0`, P256 head). It
  adds P252 (round and writeback in one clock), P253 (dispatch-clock unpack of
  S/D memory sources and moves), P254 (drops the dead multiply), P255 (S/D
  register stores packed at dispatch) and P256 (d16 and brief-indexed FP
  operands resolved in `S_FPU_DEC`).
- **B. `ad7a0d46f76ae5b4962c90f6e2267dc240ed1808`** (`ad7a0d4`, P258 head). It
  adds P257 (exception prefetch in aligned longwords) and P258 (FSAVE words
  back to back, FRESTORE reads hinted). Only `ap040_core.v` changes from A to B.

**FPU frames and FPSP.** On b2ed1b0, `fpu_frames` and `fpu_resume` pass with
the same cycle counts as the baseline. The +2 clocks that 3c3ade8 showed on
`fpu_resume` is gone. P258 makes both faster (FSAVE/FRESTORE), and both still
pass.

**Other directed checks:**

- `rtl/ap68040/tb/run_tests.sh` (31 benches) passes on both commits, in the
  default and in the LEA+XSTORE configuration. Logs are in `logs/selftest_*`
  and `p258/selftest_*`.
- `tb_ap040_fpu_normalize` passes with the release flags (10,336 cases).
  `ap040_fpu.v` is the same on both commits, so one run covers both.

**P256 addressing test (`addrtest/`).** `t_p256_addr.s` is generated by
`gen.py`. It makes 67 bit-exact checks of FMOVE/FADD/FMUL/FDIV .S/.D
operands. It covers:

- d16(An), including ±$7000 displacements;
- brief d8(An,Xn) with .W and .L index, a sign-extended negative word index
  and scales 1, 2, 4 and 8;
- d16(PC) and brief d8(PC,Xn);
- an address register as the index, and the index equal to the base;
- A7 as the base and as the index;
- a base or index written by the immediately preceding integer instruction,
  or by a preceding FP (An)+ or -(An);
- S/D stores to d16 and indexed destinations, with sentinel words either side;
- the full-format fallbacks `(bd.l,An,Xn)`, `([bd])` and `(bd.w,An,Xn)`.

It runs with caches on and with caches off (CACR=0). It passes on all four
commits.

A passive monitor (`addrtest/mon.v`) was run on b2ed1b0 to confirm that the
new path is really exercised. In each cached phase, about 40 of the
`S_FPU_DEC` clocks took `fp_inl_src` and about 40 took `fp_inl_dst`; with
caches off it was about 21 each. So both the inline path and the fallback
path are covered.

One small cost: with caches off, phase 0 is 10 clocks slower on b2ed1b0 than
on 3c3ade8 (8614 against 8604). It is equal to the baseline in phases 1 and 2.

## 3. Native FPU kernel differentials (numerical results)

The addressing risk in P256 is a wrong d16 or indexed address. That would
change results, not crash anything. So the three native Speedometer kernels
were rerun on the shipped memory path (quadra800 + sdram model):

- **Whetstone** (`native_fpu_kernel_20260928` fixture): globals, stack, ABI
  and code captures.
- **FFT** (`native_fft_buffers_20260928` capture bench): the three FFT
  payload buffers, 5,152 bytes.
- **Matrix** (`native_fpu_matrix_20260928` fixture): all 123 allocated rows,
  20,172 bytes. This capture was added here at the first free, with the same
  store-drain guard as the FFT capture (diff: `native/matrix_capture.diff`).

**Every capture is byte-identical to 0b2d265 on both commits.** For FFT and
Whetstone the reference is the archived 0b2d265 run. For Matrix a fresh
0b2d265 run was made; its loop count equals the archived one, so the capture
does not perturb timing. All three kernels pass the ABI, chip-error,
bus-error and trap-lifecycle checks. Summary: `native/native_runs_summary.txt`.

## 6. CPU Mix on ad7a0d4: does P257/P258 slow Bubble or Quick Sort?

On hardware, the ad7a0d4 seed-31 build shows Bubble Sort at 0.710 s (0.633 s
on the previous build) and Quick Sort at 0.531 s (0.516 s), the same across
five runs. To check whether the RTL itself causes this, the full-machine
Mix was run on ad7a0d4 with the same recipe as section 5: the same control
(`eafdd1b9…`), a fresh golden disk and one iteration. The Vemu is a
deterministic rebuild with SHA256 `75780da4…`, identical to the section-5
FPU run's. The run exited 0 and the setup screen is byte-identical. I
reviewed the final screen: "The tests are done!" with all values positive
and plausible. **Valid.**

| Test | 0b2d265 | b2ed1b0 | **ad7a0d4** |
|---|---:|---:|---:|
| KWhetstones/sec | 1762.002 | 1812.727 | **1830.837** |
| Dhrystones/sec | 17931.816 | 17932.124 | **17934.009** |
| Towers (s) | .479 | .479 | **.479** |
| Quick Sort (s) | .507 | .507 | **.507** |
| Bubble Sort (s) | .602 | .602 | **.602** |
| Queens (s) | .362 | .362 | **.362** |
| Puzzle (s) | .755 | .756 | **.755** |
| Permutations (s) | .712 | .712 | **.712** |
| Int. Matrix (s) | .495 | .495 | **.495** |
| Sieve (s) | .845 | .845 | **.844** |
| Average | 1.798 | 1.816 | **1.822** |

**P257/P258 do not change Bubble Sort or Quick Sort in simulation.** Every
integer row is the same as b2ed1b0 and 0b2d265 to the displayed millisecond,
except for 1 ms of rounding noise on Puzzle and Sieve. Whetstone gains again
from the cheaper FPSP trap path.

The simulation therefore does not reproduce the hardware slowdown. That fits
a fit-specific effect on the hardware build, such as the reported timing
miss on the store buffer's `s_ack -> fast_read_retire` path. It does not fit
a cycle-level change in the RTL. Two limits apply. The sim contains the real
CPU and the store buffer (`wombat_cpu`), but not the production SDRAM
controller timing or any setup/hold behaviour. Its absolute sort times also
differ from hardware (Bubble .602 in sim against .633 on the earlier hardware
build). So this result rules out an RTL cause in the modelled path; it does
not prove the cause on hardware. A timing-clean ad7a0d4 seed on hardware
would settle it.

## Verdict

Both b2ed1b0 (P252–P256) and ad7a0d4 (+P257/P258) pass every correctness
check run here against 0b2d265 with the full release macros:

- all 17 existing programs, both self-test configurations and the normalize
  bench;
- the new 67-check P256 addressing program, with caches on and off;
- the corpus-100 gate.

The FPU frame and FPSP-resume programs pass on both. On b2ed1b0 their cycle
counts equal the baseline, and P258 makes them faster.

The strongest evidence on P256's addressing is that the native Whetstone,
Matrix and FFT kernels produce byte-identical results and memory to
0b2d265, while running 13 to 38 % fewer clocks.

In the guest sim the Speedometer FPU average is 0.978 on b2ed1b0 and 0.985
on ad7a0d4, against 0.698 on the baseline. That is above the ≥0.759
hardware target, although that target itself still has to be shown on
hardware. CPU Mix (1.816) and Color8 (9.878 s) do not regress on b2ed1b0.

ad7a0d4 is qualified in simulation for an FPGA build. Quartus fit and timing
(P253's seed-21 fit missed the CPU clock) and the hardware regression gate
are still open.
